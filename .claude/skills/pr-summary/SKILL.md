# pr-summary

現在のブランチの差分（main からの差分）を解析し、設計意図と変更ファイルを含む PR 概要を markdown で生成する。

## 前提条件

- jazz-life プロジェクトのルールでは **1 PR = 1 機能 × frontend or backend のいずれか**。複数機能 / 複数レイヤを跨いだ変更を検出したらユーザに警告する。
- main ブランチが基準。`gh` が利用可能ならインストール状況を確認しておく。

## 実行手順

### 1. 差分情報を集める

並行して以下を実行:

- `git status --short`
- `git log main..HEAD --oneline`
- `git diff main...HEAD --stat`
- `git diff main...HEAD --name-only`
- 必要に応じて `git diff main...HEAD -- <path>` で個別ファイルの内容差分

### 2. レイヤとスコープ判定

変更ファイルパスを `app/backend/` / `app/frontend/` / `docs/` / その他（ルート config、`.claude/` 等）に分類。

- backend と frontend の **両方** に実コード変更があれば、PR ルール違反の可能性をユーザに警告（`make gen` のような型同期コミットは除外して良い）。
- 機能単位で 1 つかどうかも確認し、複数機能が混ざっていれば指摘。

### 3. 設計意図の抽出

以下の優先順で「なぜこの変更を入れるのか」を組み立てる:

1. ADR ([docs/000-pre-adr.md](../../docs/000-pre-adr.md)) の該当 Step ID（A-*, B-*, C-*）を特定し、その完了条件を引用
2. コミットメッセージから意図に関する記述を抽出
3. 差分そのものから機能の境界を推定

「何を変えたか」は diff を読めば分かるので、PR 概要では **WHY を中心に書く**こと。

### 4. PR 概要の生成

以下のテンプレートに沿って markdown を出力。長くしすぎず、レビュアーが 30 秒で全体像を掴めるサイズに。

```markdown
## 概要
<1-3 行で「何のための PR か」を WHY 中心に。ADR の Step ID があれば明記>

## 設計意図
- <この PR で達成したいユーザー価値 / 技術的目的>
- <代替案を退けた理由（あれば 1-2 行）>
- <既存パターンとの整合（再利用した関数 / 既存の規約への追従）>

## 主な変更
- **<カテゴリ>**: <ファイル群と変更の要旨>
- **<カテゴリ>**: ...

## 変更ファイル
<git diff --stat の主要部分を、論理的にグループ化して列挙>

## レビュー観点
- <レビュアーに特に見てほしい点 1-3 個>

## テスト
- [ ] <検証手順をチェックボックス形式で>
```

### 5. レイヤ違反の警告（該当時）

backend と frontend の両方に変更があり、生成型コミットでない場合:

```
⚠️ 注意: 本 PR は backend と frontend の両方を変更しています。
   jazz-life のルールでは「1 PR = 1 機能 × 1 レイヤ」が原則です。
   以下のいずれかを検討してください:
   - PR を 2 つに分ける
   - 一方のみコミットを残し、他方は別 PR に切り出す
```

### 6. 出力

最終的に markdown を **ユーザに表示** する（ファイルには書かない）。
ユーザが `gh pr create` を実行する際にそのままコピペできる形で。

## やらないこと

- PR の自動作成（`gh pr create` の実行）はしない。生成までで止める
- main へのマージや push はしない
- diff の全文転載はしない（`--stat` 程度に留める）
